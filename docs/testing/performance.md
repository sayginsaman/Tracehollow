# Performance and interface measurements

What this machine did with this dataset, measured on 2026-09-17 against the release candidate.
Nothing here is a benchmark against other software, and nothing is extrapolated to other hardware:
the point is that the measurement is repeatable, so you can run it on your own machine and compare.

Reproduce it with [`scripts/measure_performance.py`](../../scripts/measure_performance.py) (API
latency) and the browser checks described at the end.

## Machine and stack

| | |
| --- | --- |
| Host | macOS (Darwin 27.0.0), Apple M3 Pro, 36 GiB, arm64 |
| Docker | Engine 29.8.0, Compose v5.5.1 |
| Stack | The release candidate's images, started from `compose.yaml` with default resource settings |
| Database | `pgvector/pgvector:0.8.6-pg18-trixie`, one container, default configuration |
| Client | The measuring script on the host, over the published API port |

The stack was idle apart from the measurement: no collection, no monitors and no AI work ran at
the same time. A machine with slower storage, less memory, or other containers competing for CPU
will produce different numbers.

## Dataset

Generated by the script into a case of its own, then deleted:

| Records | Count |
| --- | --- |
| Evidence (text imports, about 350 bytes each) | 400 |
| Entities (organizations, domains, addresses, emails, accounts) | 300 |
| Relationships, each citing an evidence record | 450 |

This is deliberately larger than the documentation demo case and smaller than a long-running
investigation. It is the size at which list paging, the graph's bound and report building all do
real work.

## API latency

Each operation was called once to warm the connection, then timed over 20 calls (5 for the report
preview). Times include HTTP, the API process and PostgreSQL, but not browser rendering.

| Operation | p50 | p95 |
| --- | ---: | ---: |
| Case list (20 per page) | 5.7 ms | 6.5 ms |
| Case overview | 7.2 ms | 7.7 ms |
| Evidence list, first page of 25 | 7.0 ms | 8.0 ms |
| Evidence list, last page (offset 375) | 6.9 ms | 7.9 ms |
| Evidence record with preview | 5.2 ms | 6.3 ms |
| Entity list (50) | 8.2 ms | 13.1 ms |
| Entity search by name | 7.3 ms | 9.1 ms |
| Relationship list (50) | 9.1 ms | 10.8 ms |
| Graph, bounded to 60 nodes | 17.5 ms | 19.1 ms |
| Graph around one entity, depth 2 | 7.9 ms | 9.0 ms |
| Timeline | 7.0 ms | 7.7 ms |
| Report selection lists | 15.5 ms | 17.0 ms |
| Report preview, 25 excerpts and 10 entities | 39.4 ms | 48.8 ms |

Paging to the end of the evidence list costs the same as the first page, which is what the index
is there for. The bounded graph is the most expensive read, and it stays bounded: its cost comes
from the traversal limit, not from the size of the case.

## Import throughput

Importing the 400 text records through the API took **6.5 s in total, 16.3 ms per record**,
including hashing, duplicate detection and storage. This is single-threaded and sequential; it is
not a measure of how fast a bulk load could be made, only of what the ordinary import path costs.

Document and WhatsApp imports are processed asynchronously by the worker and are dominated by the
document itself (page count, OCR), so they are not comparable to this number and are not measured
here.

## Browser measurements

Measured with Playwright against the demonstration dataset on the same machine: five navigations
per page, median reported, `networkidle` as the end point (so this includes data fetching, not just
first paint).

| Page | Median |
| --- | ---: |
| Overview, Cases, Case overview | 577–648 ms |
| Evidence list, evidence record, entities, relationships | 621–629 ms |
| Graph page | 628 ms |
| Timeline, compare, AI, monitors, monitor detail, change set | 618–644 ms |
| Reports, imports, notifications, sources | 571–678 ms |
| Environment status | 2662 ms |
| Graph canvas painted (navigation → canvas drawn) | 78 ms |

Environment status is the outlier because it is not a page of stored data: it actively probes the
database, the broker, the evidence volume, the workers and, when AI is enabled, the model host, and
waits for each to answer.

## Accessibility and cross-engine checks

Run against the demonstration dataset, on the same candidate:

| Check | Coverage | Result |
| --- | --- | --- |
| axe-core 4.13 (WCAG 2.0/2.1/2.2 A and AA rules) | 20 pages × light and dark themes = 40 combinations | **0 violations** |
| Keyboard focus | 12 pages, 298 tab stops | Every visible stop has an outline or ring; **0 without an indicator** |
| Responsive layout | 20 pages at 390, 768 and 1280 CSS px | **No horizontal overflow** |
| Text zoom | 20 pages at 1280 px with 200% zoom (640 px effective) | **No horizontal overflow** |
| Second engine (WebKit 26, Playwright) | The same 20 pages | Every page renders with its expected heading, no overflow, **0 console or page errors** |
| Console and page errors (Chromium, both themes) | The same 20 pages | **0** |

The WebKit pass found a real defect, now fixed: engines ship different CLDR data, so
`Intl.DateTimeFormat` rendered `17 Sep 2026 at 18:29` in WebKit and `17 Sept 2026, 18:29` in Node
and Chromium. Server-rendered timestamps therefore disagreed with the browser during hydration
(React error 418) and Safari showed a different timestamp format from Chrome. Timestamps are now
composed explicitly in UTC, identically on the server and in every engine.

**Not tested:** no screen reader was used, so no claim is made about screen-reader behaviour beyond
what axe checks statically. Colour contrast was checked only by axe's automated rules. Firefox was
not tested. No assistive-technology user took part.

## Repeating the measurements

```bash
# API latency, against a disposable stack (never an installation with real cases)
TRACEHOLLOW_PERF_USERNAME=<analyst> TRACEHOLLOW_PERF_PASSWORD=<password> \
  python3 scripts/measure_performance.py --web-url http://localhost:3160 --json results.json
```

The browser checks use Playwright from `apps/web` with `axe-core` injected into each page, signed
in against the demonstration dataset ([../guides/demo-dataset.md](../guides/demo-dataset.md)), and
run the same route list in Chromium (light and dark) and WebKit.
